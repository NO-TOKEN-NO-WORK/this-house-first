# ADR-0008: 알림은 v0에서 인앱으로 전달한다 (Web Push는 스트레치)

- **상태**: 승인됨
- **날짜**: 2026-08-22
- **결정자**: 팀 전원

## 맥락 (Context)

F3는 경보일 아침 8시 푸시("오늘 비상 단계입니다…")를, F4는 승격 시 관리자 알림을 요구한다. 진짜 Web Push(VAPID)는 구독 관리, iOS의 홈 화면 설치 요구, 권한 UX까지 딸려 오는 작업이고, 데모 시나리오(PRD §10)는 "알림 도착" 장면을 보여주면 충족된다. 알림 피로 방지(비경보일 0건)가 스펙이다(PRD §9).

## 결정 (Decision)

- v0 알림은 **인앱 알림**으로 구현한다: 경보일 보드 상단 배너 + 승격 이벤트 피드. 데모에서는 관리자 화면의 트리거 버튼([ADR-0011](0011-deploy-local-demo-first.md))이 담당자 화면에 알림을 띄우는 흐름으로 시연
- 갱신 전달은 폴링(수 초 간격)으로 시작하고, 필요 시 SSE로 교체
- **Web Push(VAPID)는 스트레치 골**: D2에 여유가 있을 때만, 별도 브랜치에서

## 근거 (Rationale)

- 데모 가치(알림 장면) 대비 Web Push 구현 비용이 과함 — iOS 제약이 특히 시간 도둑
- 알림 정책(비경보일 침묵, 요약 1건 + 승격만)은 전달 수단과 무관하게 도메인 로직으로 구현되므로, 수단은 나중에 업그레이드 가능

## 검토한 대안 (Alternatives)

- **Web Push 정면 구현** — 데모 리스크(권한 거부, iOS) 대비 이득 없음. 스트레치로 강등
- **FCM** — 네이티브 앱 아님, 의존 추가. 기각
- **SMS(알리고 등)** — 실배포 로드맵에선 유력하나 데모엔 불필요·유료. 기각

## 결과 (Consequences)

- 긍정: 데모 시나리오 충족 + 구현 반나절
- 부정/트레이드오프: 앱을 열어야 알림이 보임 — 실배포 갭으로 문서화하고 발표에서 로드맵으로 언급
- 되돌리기: 알림 생성(도메인)과 전달(수단)을 분리해 두므로 Push 추가는 전달층 교체

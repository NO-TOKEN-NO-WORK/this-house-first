# ADR-0024: 대상자 맥락 브리핑 — 근거 인용 강제 + 위험도 미개입

- **상태**: 승인됨
- **날짜**: 2026-08-23
- **결정자**: 팀 전원

## 맥락 (Context)

담당자가 대상자를 만날 때 쓰는 사전 정보는 두 가지뿐이다. 전원에게 똑같은 고정 질문 3개(`CALL_GUIDE_QUESTIONS`)와, 최근 확인 기록 3건의 **원문 나열**(`SubjectInformationSections.tsx`의 방문 히스토리)이다. 개인별 맥락 — 이 어르신은 낮에 밭에 나가는지, 에어컨 리모컨이 고장이라 했었는지, 지난달부터 어지럽다는 말을 반복하는지 — 는 담당자의 기억에만 있다. 담당자가 바뀌거나 대체 근무가 들어오면 그 맥락은 0으로 리셋된다.

자유 서술 메모(`CheckEvent.memo`)는 이미 쌓이고 있지만 쓰이는 곳이 두 군데뿐이다. 화면이 원문을 그대로 뿌리거나, 복지 스캔이 허용 단어 목록에 걸리는지만 본다([ADR-0020](0020-welfare-scan-luna-responses.md)). 의미는 버려진다.

동시에 두 개의 기존 결정이 이 기능을 제약한다.

- [ADR-0005](0005-rule-based-risk-model.md): 위험도는 규칙 기반이고 ML을 배제한다. 화면의 위험 판단은 엔진이 낸 `reasons`만 표시한다.
- [ADR-0020](0020-welfare-scan-luna-responses.md): 자유 서술 메모는 외부로 보내지 않는다. 정규식만으로 비정형 이름·전화번호를 완전히 제거할 수 없기 때문이다.

## 결정 (Decision)

`CheckEvent` 이력에서 **대상자 맥락 브리핑**을 생성한다(FR-12). 산출물은 세 개다.

- **AI 대화 추천** — 전화 안내의 고정 질문 3개 아래에 별도 묶음으로 붙는 대상자별 질문 최대 2개. 어르신께 그대로 여쭐 말·질문 이유·근거 기록을 함께 보여 준다.
- **인수인계 카드** — `/today/[subjectId]` 3줄: `생활 리듬` / `반복 신호` / `조심할 것`. 각 줄에 근거 기록의 날짜와 결과를 붙인다. 대상자 정보 화면은 `AI 요약` 탭이(화면 이름은 Figma를 따른다 — ADR-0014 결과 1), 대상자 상세는 위험 사유 아래 카드가 같은 목록을 읽는다 — 담당 교체가 화면 한 장으로 끝나야 하기 때문이다.

  > **갱신 (2026-08-23, Figma `ver 5` `164:8144`)**: 방문 화면(`VisitDetailView`)에서는 이 카드를 뺐다. 개정된 디자인이 문 앞에서 읽을 것을 위험 사유·방문 체크리스트로 좁혔다 — 맥락은 보드 카드 chevron 한 번으로 여는 `대상자 정보` 탭에 그대로 있고, 전화 흐름의 대화 추천도 그대로다 (ADR-0014 결과 11).
- **기록별 대화 요약** — 대상자 정보의 방문 히스토리 행을 열면 해당 `CheckEvent.memo`의 핵심과 진행 중인 사항을 보여 준다. 녹음 파일이 없는 현재 데이터 모델에서는 파일명을 만들거나 음성 내용을 추정하지 않는다.

### 경계 (이 ADR의 본체)

1. **AI는 위험도에 개입하지 않는다.** 브리핑은 `RiskAssessment.score`·`grade`·`reasons`에 절대 쓰지 않고 읽지도 않는다. 누구부터 확인할지는 [ADR-0005](0005-rule-based-risk-model.md)의 규칙 엔진이 단독으로 정한다. 브리핑이 답하는 질문은 "왜 이 사람인가"가 아니라 "만나서 무엇을 확인할까"다.
2. **모든 문장은 근거 기록을 인용한다.** 모델은 문장마다 `sourceCheckEventId`를 함께 내야 한다. 서버는 그 id가 실재하고 **해당 대상자의 것인지** 대조하고, 통과하지 못한 문장은 버린다. 화면에 나가는 근거 문구(날짜·확인 종류·결과)는 모델 출력이 아니라 서버가 가진 `CheckEvent` 행에서 만든다. 위험 사유를 UI가 재작성하지 않는 원칙(AGENTS.md 도메인 규칙 3)을 그대로 확장한 것이다.
3. **지시하지 않는다.** 브리핑은 무엇을 확인할지만 제안하고 의료 판단·처방·복지 자격 판정을 하지 않는다. 자격 판정은 계속 `welfare-scan/eligibility.ts`의 규칙 엔진이 한다.
4. **알림을 만들지 않는다.** `Notification` 행을 생성하지 않는다(AGENTS.md 도메인 규칙 4). 비경보일에도 열람만 가능하다.
5. **실패는 현재 화면으로 폴백한다.** 생성 실패·인증 미설정·근거 전량 폐기 시 브리핑 영역만 사라지고 원문 히스토리는 그대로 보인다. 담당자 작업은 막히지 않는다.

### 개인정보 경계 (ADR-0020 부분 대체)

- **1명 단위 온디맨드.** 담당자가 그 대상자를 열었을 때 그 1명분만 보낸다. 관리자 일괄 배치는 하지 않는다.
- **전송 전 서버 마스킹.** 사람 이름·전화번호·주소/지번·기관명 패턴을 `CheckEvent.memo`에서 제거한 뒤 보낸다. `Subject.id`·`name`·`phone`, 건물 주소, 담당자 이름은 어떤 형태로도 보내지 않는다. 요청이 한 대상자분뿐이라 대상자 식별자 자체를 싣지 않고, 기록 id만 호출별 임시 별칭(`event-1`)으로 바꾼다.
- `store: false`, strict Structured Outputs를 유지한다.
- **전제**: 대상자는 전원 합성 인물이다(PRD §8 "건물은 진짜, 사람은 가짜"). 이 전제가 깨지면 이 결정도 깨진다.
- **실배포 게이트**: 실제 대상자 기록으로 이 경로를 쓰려면 지자체 위탁계약의 처리 범위 명시와 담당자 고지가 선행 조건이다. 코드가 아니라 계약이 막는 부분이므로 이 ADR에 남긴다.

### 구현

- 모델 호출은 기존 경로를 재사용한다: Vercel AI Gateway Responses API, `openai/gpt-5.6-luna`([ADR-0023](0023-vercel-ai-gateway-luna.md)). reasoning effort는 `medium`이다 — 산출물이 3줄이고 담당자가 화면을 여는 동안 기다리는 호출이라 지연이 정확도보다 비싸다(복지 스캔의 `high`와 다른 이유).
- `SubjectBriefing` 모델 한 개를 추가해 캐시한다. `subjectId` unique + 생성 근거가 된 최신 `CheckEvent.id`를 함께 저장하고, 대화 추천 2개·인수인계 3줄·최근 기록별 대화 요약을 JSON 직렬화해 둔다. 열람 시점의 최신 기록 id와 다르면 재생성하며 새 기록이 없으면 다시 호출하지 않는다. 근거 부족으로 결과가 비어도 최신 기록 기준 빈 결과를 캐시해 같은 입력으로 모델을 반복 호출하지 않는다.
- 조회는 `GET /api/subjects/[subjectId]/briefing` 하나다. 클라이언트가 모델을 직접 부르지 않는다.
- **근거 대조는 DB를 모르는 순수 함수에 둔다**(`lib/briefing/evidence.ts`). 이 경계가 이 기능의 안전장치이므로, prisma 목을 세워야만 돌아가는 자리에 두면 검사되지 않은 채 바뀐다. `service.ts`는 캐시와 DB만 맡는다.
- 산출물 상한은 `domain.ts` 상수 하나에서 나온다(`BRIEFING_MAX_LINES`·`CONVERSATION_SUGGESTION_MAX`·`CONVERSATION_SUMMARY_MAX`·`CONVERSATION_ONGOING_MAX`). 모델에 보내는 스키마와 화면이 같은 값을 읽어야 "3줄을 넘지 않는다"가 한 곳에서 지켜진다.
- 화면의 근거 문구는 요일을 뺀 짧은 날짜(`8/14 전화 · 괜찮았어요`)다. 전화 안내 다이얼로그 안에서 한 줄을 넘기지 않아야 하기 때문이며, 히스토리 목록·기록 상세는 화면이 넓어 요일까지 읽는다.
- 시드는 과거 경보일 3일(오늘 기준 -9·-7·-2일)과 대상자별 확인 기록·메모를 만든다. 문장은 `prisma/seed/history.ts`에 **대상자별로 따로 적는다** — 몇 개 템플릿을 돌려 쓰면 15명의 브리핑이 서로 구분되지 않아 "이 어르신은 새벽에 밭에 나가십니다"라는 데모 장면(PRD §10)이 성립하지 않는다. 대상자마다 최소 2건을 두어 `반복 신호`와 기록별 대화 요약이 나올 입력을 보장한다. 날짜는 오늘 기준 상대값이라 언제 시드를 돌려도 "최근 기록"이 된다. 오늘 날짜의 경보·평가·가구 상태는 만들지 않아 평상시 데모 첫 화면을 바꾸지 않는다.

## 근거 (Rationale)

- 담당자 교체 시 맥락이 사라지는 문제는 가중치로 풀리지 않는다. 규칙 엔진이 원리적으로 못 다루는 자리라서 LLM을 쓰는 이유가 명확하다.
- 근거 인용 강제는 이 도메인에서 환각이 곧 잘못된 돌봄이기 때문이다. 없는 사실 한 줄이 현장 대응을 틀어지게 한다. 서버가 id를 대조해 버리는 방식은 모델을 믿지 않고도 출처를 보장한다.
- 위험도 미개입 경계는 제품 논지를 지킨다. "예측이 아니라 배분"이라는 주장과 전 가중치 출처 명기(PRD §7)가 이 시스템의 방어선인데, AI가 점수에 손대는 순간 둘 다 무너진다.
- 1명 단위 온디맨드는 외부로 나가는 자유 서술의 양을 담당자가 실제로 그 대상자를 만나려는 순간의 1명분으로 묶는다. 배치보다 노출면이 작고, 캐시 키가 자연스럽게 대상자 1명이 된다.

## 검토한 대안 (Alternatives)

- **ADR-0020 경계 유지(허용 단어만 전송)** — 개인정보 방어는 가장 강하지만 모델이 보는 것이 단어 목록이라 "맥락 이해"가 규칙 템플릿으로 축소된다. 기능을 넣을 실익이 없어 기각.
- **관리자 일괄 배치 생성** — 인수인계 카드를 미리 만들어 둘 수 있지만, 외부로 나가는 자유 서술이 대상자 수만큼 늘고 아무도 열어보지 않을 대상자까지 포함된다. 기각.
- **브리핑을 위험 점수에 반영** — "어지럽다 반복"이 위험도에 들어가면 설명 가능성과 재현성이 동시에 깨지고 ADR-0005를 뒤집는다. 반복 신호는 브리핑 문장으로만 남긴다. 기각.
- **캐시 없이 매 열람마다 생성** — 마이그레이션은 아끼지만 담당자가 카드를 누를 때마다 수 초를 기다린다. 화면당 결정 1개·빠른 기록(PRD §9)과 충돌해 기각.
- **메모를 구조화 입력으로 대체(탭 입력 확장)** — 개인정보 경계는 유지되나 담당자 기록 부담이 늘고, 서술로만 남는 뉘앙스가 사라진다. 기각.

## 결과 (Consequences)

- 긍정: 이미 쌓이던 `CheckEvent.memo`가 처음으로 담당자에게 되돌아온다. 담당자 교체·대체 근무에서 맥락 인계가 화면 한 장으로 끝난다. 위험도 엔진과 심사 방어 논리는 그대로다.
- 부정/트레이드오프
  - `Subject`에 종속된 `SubjectBriefing` 모델과 마이그레이션이 하나 늘어난다.
  - 기록이 적은 대상자는 브리핑이 1줄이거나 아예 없다. 빈 상태를 정상으로 표시해야 하며 문장을 채우려고 근거 없는 추측을 넣지 않는다.
  - 시드에 합성 확인 기록 이력을 만드는 작업이 선행돼야 한다. 이 기능의 실제 작업량 대부분이 여기다.
  - 마스킹은 완전하지 않다. 이 결정은 대상자가 합성 데이터라는 전제 위에 서 있고, 실데이터 적용은 계약 게이트를 통과해야 한다.
- 되돌리기: 브리핑은 별도 라우트·별도 모델·별도 화면 영역에 격리돼 있다. 라우트를 끄면 화면은 원문 히스토리만 있는 현재 상태로 돌아간다. 스코어링·상태머신·알림 경로는 이 기능을 알지 못한다.
